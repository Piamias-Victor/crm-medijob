# Job board sync via the site’s Supabase, not its HTTP API

The CRM must publish JobOffers and ingest Applications without changing medijob-jobs. The public `POST /api/offres` exists but needs a Netlify `ADMIN_PASSWORD` we do not have; `source_crm_id` would send applicants to Tool4Staffing.

Decision: the CRM talks to the job-board Supabase project as a client — write **`offres`** (the public listing table the site reads), read **`candidatures`** (the table `/api/candidatures` inserts into). It stores the board listing id on the JobOffer, does not call the site HTTP API, does not set `source_crm_id`, and does not use `offres_emploi`, `candidats`, `missions`, or other old-CRM tables in that same database. Spontaneous rows (`offre_id` empty) are ignored in V1. Unpublish sets `publiee = false` on that `offres` row; the CRM never deletes job-board rows. Public listing `entreprise` is the Pharmacy name; `contact_email` is a Medijob address from env (`JOBS_CONTACT_EMAIL`), never the pharmacy or a Tool4Staffing alias. Listing body otherwise maps from JobOffer (title/content) and Mission (JobTitle, contract, hours, pay, start) plus Pharmacy location. The board CV URL is stored on the Application at ingest; on accept the file is copied into CRM Candidate storage (create Candidate even if copy fails). When the Mission becomes POURVU or ANNULEE, a published JobOffer is unpublished (`publiee = false`) automatically. CRM `PUBLIEE` is set only after the `offres` write succeeds; a board error leaves the JobOffer unpublished and surfaces in the UI.
